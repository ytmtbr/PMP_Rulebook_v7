07 Scope & Requirements

Rule 1　Predictive Scopeの基本Flow

Collect Requirements ↓ Define Scope ↓ Create WBS ↓ Scope Baseline ↓ Validate Scope ↓ Control Scope
WBSから始める。 Scheduleから考える。
Requirements First ↓ Scope ↓ WBS

Rule 2　Requirements Conflict

Conflicting Requirements ↓ Review RTM ↓ Trace to Source / Business Objective ↓ Review Priority ↓ Facilitate Agreement

Stakeholder同士でRequirementの優先順位が衝突した場合、 RTMを客観的な共通参照点として使う。

Scope Statementだけを見る。 Communication Planを見る。 PMが独断で優先順位を決める。
Requirement Conflict = RTM

Rule 3　Requirements Traceability Matrix

Requirement ↓ Source ↓ Business Objective / Need ↓ Priority ↓ Deliverable ↓ Verification / Status

RTMはRequirementがどこから来て、 どの成果物で満たされ、 どう検証されるかを追跡する。

RTM ＝ Task管理表。 完了Requirementを変更時に削除する。
Trace Requirements from Origin to Verification

Rule 4　Scope Baseline

Project Scope Statement + WBS + WBS Dictionary = Scope Baseline
ScheduleをScope Baselineに含める。 Cost Baselineを含める。 RTMをScope Baselineそのものと考える。
Scope Baseline = Scope Statement + WBS + WBS Dictionary

Rule 5　WBS

Project Scope ↓ Deliverables ↓ Sub-deliverables ↓ Work Packages

WBSはScopeを管理可能な単位まで 階層的にDecomposeする。 基本はDeliverable-oriented。

Activity一覧をそのままWBSにする。 担当者一覧をWBSにする。 Scheduleを先に作ってWBSを逆算する。
WBS = Deliverable-oriented Scope Decomposition

Rule 6　WBS Dictionary

Work Package ↓ Detailed Description ↓ Acceptance / Quality Information ↓ Assumptions / Constraints ↓ Responsible Organization / Other Planning Details

WBS Dictionaryは、 WBS上の各Componentについて詳細情報を補足する。 内容はProjectやOrganizationによって異なり、 担当組織・Schedule Milestone・Cost Estimateなどを 含むこともある。

WBS Dictionaryを単なるRequirement一覧と考える。 WBSと同じ情報しかないと考える。
WBS shows WHAT. Dictionary explains the DETAILS.

Rule 7　Requirements Gathering

Identify Stakeholders ↓ Engage Stakeholders ↓ Interviews / Workshops / Observation / Other Techniques ↓ Document Requirements ↓ Analyze / Prioritize
PMだけでRequirementsを書く。 SponsorだけからRequirementsを集める。 全Stakeholderを同じ重要度で扱う。
Requirements come from Stakeholder Needs

Rule 8　Requirement Change

New / Changed Requirement ↓ Impact Analysis ↓ Formal Change Request ↓ Approval ↓ Update Scope Baseline / RTM / Relevant Plans ↓ Implement

PredictiveまたはFormal Governance下では、 Requirement変更も正式なChange Controlを通す。

RTMだけ更新して実装。 Sponsor要求だから即追加。 Backlogへ非公式に追加。
Requirement Change = Analyze ↓ Approve ↓ Update ↓ Implement

Rule 9　Predictive Scope vs Agile Scope

Predictive Agile / Adaptive
Scope Baseline Product Backlog
WBS Epics / Features / User Stories
Scopeを比較的早期に詳細化 Progressive Elaboration
Formal Change Control Backlog Reprioritization

建設などScopeが比較的安定したProjectではWBSが強い。 不確実性が高いProduct Developmentでは Backlogを継続的にRefineする。

Agileでは絶対にWBSを使えない。 Hybridでも必ずどちらか一方だけを選ぶ。
Stable Scope → Baseline / WBS Evolving Scope → Backlog / Refinement

Rule 10　Control Account

Scope + Schedule + Budget ↓ Control Account ↓ Performance Measurement

Control Accountは、 Scope・Schedule・Costを統合して 管理するManagement Control Point。

WBS Dictionaryを選ぶ。 Scope Baselineだけを選ぶ。 Planning Packageと混同する。
Control Account = Scope + Schedule + Cost Integration Point

Rule 11　ReadyなBacklog Item

Clear ↓ Small Enough ↓ Testable ↓ Acceptance Criteria ↓ Understood / Estimated ↓ Ready
Acceptance Criteriaなし。 EpicのままSprintへ入れる。 説明文を増やしただけでReady。
Ready = Clear + Testable + Actionable

Rule 12　Validate Scope vs Control Scope

Validate Scope Control Scope
成果物のFormal Acceptance Scopeの状態をMonitor
Customer / Sponsor Acceptance Scope Changeを管理
Accepted Deliverables Prevent Scope Creep
Quality ControlとValidate Scopeを同じものと考える。 Validate ScopeをScope変更管理と考える。
Control Quality → Correct? Validate Scope → Accepted?

Rule 13　Scope Creep

Unapproved Scope Addition = Scope Creep 发现 ↓ Stop / Clarify ↓ Impact Analysis ↓ Formal Change Process

価値がありそうな追加機能でも、 正式な承認なしにScopeへ追加しない。

顧客が喜ぶから追加。 Teamに余裕があるから追加。 Sponsorが口頭で頼んだから追加。
Good Idea ≠ Approved Scope

Rule 14　Scope Summary

Requirements ↓ Define Scope ↓ WBS / Backlog ↓ Agree / Baseline ↓ Deliver ↓ Validate ↓ Control Changes

試験で迷ったら

  • PredictiveではRequirements → Scope → WBS
  • Requirement ConflictならRTM
  • Scope Baseline = Scope Statement + WBS + WBS Dictionary
  • WBSはDeliverable-oriented
  • Requirement変更はImpact Analysisから
  • Formal環境ではChange Controlを通す
  • AgileではBacklog RefinementでScopeを詳細化する
  • Control AccountはScope・Schedule・Costの統合点
  • Validate ScopeはFormal Acceptance
  • Scope Creepを許さない
Requirements First ↓ Deliverable-oriented ↓ Formal Change
